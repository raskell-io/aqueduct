# Embedded engine benchmark: Apple M4, macOS, APFS

- **Date:** 2026-10-31
- **Machine:** Apple M4 (10 cores), 16 GB, internal SSD, APFS, macOS 26.5.1; rustc 1.99.1, release build
- **Tool:** `cargo run --release -p aqueduct-bench-engine` (benches/engine)
- **Workload:** a Rust workflow (SDK) of three sequential steps whose bodies return their input, so the
  numbers are the engine's own. Every run journals 8 entries. 8 workers. Checkpoints every 10,000
  records (the default).
- **Latency:** from calling `Engine::start` to the first step's body starting on a worker. Each client
  starts one run, measures, waits for the run to finish, and starts the next.
- **Throughput:** clients start 20,000 runs in total as fast as `start` returns (it returns once the start
  is durable), then wait for all of them; entries per second over the whole time.

## Reading the numbers

- With `Fsync`, start to first step costs one flush: the `Started` entry and the first step's
  `StepScheduled` are written in the same batch, and the dispatch is released after that batch's
  `F_FULLFSYNC`. The p50 of about 4 ms is the device's flush time (compare
  [the fsync baseline](2026-10-31-fsync-m4.md)); 16 concurrent clients share flushes and barely move it.
- Throughput grows with concurrency because group commit puts more entries into each flush: with 256
  clients, about 4 ms per flush carries several hundred entries. A single client cannot reach 50,000
  entries per second with `Fsync` on this machine; the target is about concurrent load.
- With `Os`, latency is the engine's own: about 10 µs for one client. The maximum of about 14 ms in both
  runs, far above the p99, matches a checkpoint: checkpoints commit redb with an fsync on the partition's
  thread, so a request that arrives during one waits for it. Moving checkpoints off the request path is
  the obvious improvement when tail latency matters.
- `Os` throughput (about 330,000 entries per second) is bounded by the single partition thread and the
  workers, not the disk.
- `Durability::Os` was checked with the engine crash harness (`cargo xtask crash-engine --os`): 100 random
  `kill -9`s, 8,419 acknowledged runs, all ended as the reference says. It does not survive a power loss
  or a kernel crash; it is for tests, tools and measurements (BRIEF.md section 7).
