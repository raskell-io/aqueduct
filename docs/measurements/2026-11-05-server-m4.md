# Single server benchmark: Apple M4, macOS, APFS

- **Date:** 2026-11-05
- **Machine:** Apple M4 (10 cores), 16 GB, internal SSD, APFS, macOS 26.5.1; rustc 1.99.1, release build
- **Tool:** `mise run bench:server` (benches/server); `-- --quick` for a short run, `-- <section>` for one
- **Setup:** `serve_with`, as `aqueduct server` uses it, on a real loopback socket, with default limits unless
  a row says otherwise. Runs are started with a key and a one-word input; the workflows are Rust workflows, so
  no procedure interpreter is involved, and steps do nothing. Each row is 5 seconds of closed-loop clients on
  8 gRPC connections, or one connection per client for HTTP, against a fresh data directory. Afterwards, the
  benchmark checks that every acknowledged start is a run in the engine.
- **Latency** is from sending a request to its answer: for a start, until it is durable.

**How far to trust these.** The load generator is in the same process, on its own runtime, so it uses the
same 10 cores as the server. The machine was not idle: the load average was about 5.5 before the runs, and
other processes were using CPU throughout. The two runs differ by up to about 25% in rows that should be the
same, so differences smaller than that are not findings. p99s and maximums in particular are noisy here:
earlier short runs had a p99 of about 5 ms for one client, against 21 to 25 ms here. These are lower bounds on
a quiet machine, not measurements of one. Linux is not measured.

The target needs concurrency: group commit carries more starts in each flush. With 64 clients the rate is
5,500 to 6,300 per second, and with tokens 1,800 to 3,200. One client gets about 200 per second without tokens
and 120 with, because each start waits for one flush (about 4 ms), or two with the audit log.

## What this measurement changed

Three problems showed up, and were fixed before the numbers below. The "before" numbers are from short runs
(1 second per row), so they compare orders of magnitude, not percentages. The token row compares two short
runs: within a second of the tokens file changing, every request reads it again, which dominates both numbers.
There is no "before" for a settled file, so the runs below (50,864 to 55,462 reads per second) do not show how
much of that is this fix.

| | before | after |
|---|---:|---:|
| starts per second, tokens and audit, `Fsync`, 256 clients | 251 | 8,272 to 9,394 |
| the same, p50 | 721 ms | 24 to 27 ms |
| reads per second, 1,000 tokens, in the first second after the file changed | 1,756 | 3,174 |
| transport errors under overload, 1,024 clients | 823 | 0 |
| transport errors under overload, 4,096 clients | 12,006 | 0 |

- **The audit log capped the server at its disk's flush rate.** Every line had its own `F_FULLFSYNC`, one at a
  time, so an audited server managed about 250 actions per second whatever else it did (`Durability::Os` did
  not help). Concurrent lines now share one write and one sync. A line is still synced before its request is
  answered, and the chain is unchanged.
- **Refusing a request could fail other requests.** Answering before the request's body was read reset the
  HTTP/2 stream, and a client still sending saw a transport error instead of the retryable answer. Enough
  resets also made h2 close the connection, which failed every other request on it. Refusals now read a small
  body first. A test on the real stack (`shedding_answers_every_request_and_keeps_the_connection`) failed with
  `Cancelled` and `Unknown` in all three tries without this change.
- **Every request cloned the tokens.** The list is now shared. (A request after the file changes still reads
  it again for one second, because a change within the clock's resolution can keep the same time.) The token check and the lookup of the token's
  namespace are now one lookup, so a token that passes always has its namespace.

## Reading the numbers

- **Tokens and the audit log cost about 40% of start throughput,** with `Fsync` at 256 clients (12,489 to 16,721
  without; 8,272 to 9,394 with), and a second flush of latency: 8 ms instead of 4 for one client. An audit line
  is written after the action it records, so a start waits for two flushes in turn. Both are on one disk.
  Read requests are not audited: tokens cost them little (51,271 to 61,217 per second, against 68,556 to 72,958).
- **`Fsync` is what limits starts.** With `Os`, gRPC reaches 39,000 to 52,000 per second, about the same at 64
  and 256 clients, so the limit moves to CPU.
- **gRPC and HTTP/JSON are about the same.**
- **Namespaces cost nothing measurable.** A named namespace was within the noise of the default one.
- **Parked runs cost nothing without a cap,** up to 100,000. **With a cap, 100,000 parked runs halve start
  throughput** (about 7,800 per second, against 14,755 to 16,926). The cap's running count is recomputed by
  scanning every run after each flush. This is not fixed: it should become a counter kept up to date as runs
  end. It only affects servers with `max_running_runs` or a namespace's cap, at about that many runs.
- **Overload holds.** With 16 times as many clients as places, the server still starts 12,000 to 13,800 per
  second and answers the rest (170,000 to 200,000 a second) with a retry hint, with no errors. Allowing fewer
  concurrent requests lowers throughput: 64 places allow 4,300 to 5,100 starts per second, since places limit
  how many starts share a flush. The default of 256 should not be lowered without measuring.
- **Remote steps.** Start to first step at a worker over gRPC is 4.4 to 4.7 ms at p50 for one client, about one
  flush. A three-step run takes about 18 ms from start to result: four flushes. At 256 clients, 5,100 to 6,700
  three-step runs a second.
- **Draining a backlog:** 13,000 to 18,500 steps per second, and the number of namespaces has no effect above
  the noise. **The rate falls as the backlog grows:** short runs drained a backlog of 2,000 at about 79,000 steps
  per second, and this one of 20,000 at about 18,000. This is not fixed, and the cause is not confirmed.
  `StepQueue::complete` scans the waiting and issued lists for each result, which would explain it; the machine
  and the run length also differ between those two numbers.

## Not measured yet

- Linux, a quiet machine, and clients on another machine.
- TLS. Payloads larger than a few bytes.
- Procedures (the interpreter's cost) and workflow workers over the network.
- Long runs, and a server restarted with a large log.
- Rate limits at high caller counts.
