# Storage benchmark: Apple M4, macOS, APFS

- **Date:** 2026-10-31
- **Machine:** Apple M4 (10 cores), 16 GB, internal SSD, APFS, macOS 26
- **Tool:** `cargo run --release -p aqueduct-bench-storage` (benches/storage)
- **Engines:** a plain framed log file (`aqueduct-storage::frame`), redb 4.4.0, fjall 3.1.13. All three sync
  with `F_FULLFSYNC` on macOS.
- **Payloads:** 256-byte log records and 512-byte run state, incompressible pseudo-random bytes. A first run
  with constant bytes favoured fjall, which compresses with LZ4, so it is not reported.

The two runs below were taken a few minutes apart; the variation between them is mostly the device
(compare the fsync baseline, `2026-10-31-fsync-m4.md`).

## Observations

- Durable appends are bound by the flush: up to 128 records per commit, all three engines are within
  noise of each other at about 4.5 to 5 ms per commit. At 1,024 records per commit the plain log is fastest
  in both runs; fjall varies between runs; redb is slowest, consistent with copy-on-write B-tree pages.
- Without fsync, the plain log appends 2.1 to 2.6 million records per second, fjall 1.4 to 1.6 million,
  redb 0.6 to 0.9 million.
- Reopening after a clean shutdown takes about 4 ms for redb and 1 to 1.5 s for fjall (journal replay) at
  200,000 records.
- Random point reads of run state: redb 182,000 to 407,000 per second (a read transaction per read), fjall
  155,000 to 163,000.
- Space: redb 270 MB, fjall 164 MB, the plain log 54 MB for its share; the raw data is about 160 MB.
