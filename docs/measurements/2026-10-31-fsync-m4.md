# fsync baseline: Apple M4, macOS, APFS

- **Date:** 2026-10-31
- **Machine:** Apple M4 (10 cores), 16 GB, internal SSD, APFS, macOS 26 (Darwin 25.5)
- **Tool:** `cargo xtask fsync` (256-byte entries, appended to one file in the temp directory)
- **Rust:** 1.99.1. On macOS, `File::sync_all` and `File::sync_data` both issue `F_FULLFSYNC`.

Two runs, a few minutes apart:

| | run 1 | run 2 |
|---|---|---|
| `sync_all`, one entry per sync, p50 | 4.12 ms | |
| `sync_all`, one entry per sync, p99 | 8.11 ms | |
| `sync_data`, one entry per sync, p50 | 4.14 ms | 3.94 ms |
| `sync_data`, one entry per sync, p99 | 6.26 ms | 5.27 ms |

Group commit, `sync_data` after each batch:

| batch | entries/s (run 1) | entries/s (run 2) | batch p99 (run 1) | batch p99 (run 2) |
|---:|---:|---:|---:|---:|
| 1 | 240 | 188 | 6.0 ms | 25.1 ms |
| 8 | 1,573 | 1,467 | 25.7 ms | 27.5 ms |
| 64 | 12,360 | 15,942 | 26.6 ms | 5.0 ms |
| 256 | 59,037 | 66,491 | 5.9 ms | 4.8 ms |
| 1,024 | 193,414 | 273,240 | 25.6 ms | 4.1 ms |

Observations:

- A full flush costs about 4 ms regardless of batch size up to 256 KiB, so throughput is roughly
  `batch size / 4 ms`. 50,000 durable appends per second needs batches of about 200 entries.
- p99 shows occasional spikes of about 25 ms that do not depend on batch size; they come from the device.
- Not yet measured: Linux `fsync`/`fdatasync` on NVMe (the cluster reference setup), and plain macOS
  `fsync` without `F_FULLFSYNC` (which is not durable against power loss).
